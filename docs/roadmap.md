# AI Studio 生产化路线图

> 本路线图从品牌素材 mock 垂直切片出发。除“阶段 0”验收通过的条目外，后续内容均为计划或生产缺口，不代表已经实现。

## 1. 分期原则

- 每一阶段都交付可独立验证的业务结果，并设置进入下一阶段的门禁。
- 先验证用户工作流，再承担真实模型成本；先建立安全和可观测性，再扩大流量。
- 保持模块化单体，直到独立扩缩容、故障隔离或团队边界明确证明拆分收益。
- 对外契约由协调者统一演进；架构建议不能绕过共享契约直接进入实现。

## 2. 阶段计划

### 阶段 0：可运行的 mock 垂直切片

目标：证明“选模板 -> 输入 -> 运行 -> 查看节点 -> 下载资产 -> 失败重试/取消”的完整体验。

交付：

- image/video/coding 模板目录，只有品牌图片模板 enabled。
- 实施简报约定的 API、统一错误信封和配置化 base URL。
- 确定性本地 mock adapter、零成本和持续 mock 标签。
- 持久化 run 状态、启动恢复、创建幂等、retry/cancel。
- Web 轮询、历史记录、节点图、资产 gallery 和可下载结果。
- 自动化测试、Web build 和 `docs/acceptance.md` 的验收证据。

退出门禁：所有阻断验收项通过；任何部分实现均明确记录，不能用演示文案掩盖。

### 阶段 1：受控内部 alpha

目标：让内部用户在不产生真实模型费用的条件下稳定试用，并补齐生产基础面。

交付：

- 身份认证、workspace/tenant 授权和最小 RBAC。
- PostgreSQL 迁移、对象存储、备份与恢复演练。
- 独立 worker + 持久队列、租约/心跳、死信和管理式 reconcile。
- request/trace ID、结构化日志、指标、告警和基础 SLO。
- 速率限制、请求体限制、资产保留/删除、审计日志。
- 模板 revision 可见性和受控发布流程。

退出门禁：租户隔离测试通过；恢复演练满足 RPO/RTO；队列重复投递不产生重复资产；审计可追踪一次 run 的创建、执行、取消和下载。

### 阶段 2：单一真实图片供应商 beta

目标：在白名单用户和硬预算上限下验证真实品牌图片生成。

交付：

- 一个经过安全评审的真实 image adapter；mock 模式仍保留并明确区分。
- 供应商密钥托管、模型/区域 allowlist、网络出口控制。
- `externalOperationId`、供应商幂等键、`outcome_unknown` reconcile 和人工处置队列。
- 配额、预算上限、成本预估/实际用量核对、熔断和指数退避。
- prompt/输出内容政策、拒绝原因、资产隔离与审核流程。
- 服务条款、隐私、数据驻留和供应商保留政策评审。

退出门禁：故障注入覆盖超时、429、5xx、回调丢失和供应商接受结果未知；不会自动重复收费；成本偏差和安全事件有告警及停机开关。

### 阶段 3：图片能力正式生产

目标：把已验证的图片工作流开放给目标客户并具备稳定运营能力。

交付：

- 多供应商路由或明确的单供应商降级策略。
- 计费账本、对账、退款/补偿规则和客户配额。
- 分页/过滤、资产生命周期、删除导出、支持工具。
- 容量模型、自动扩缩容、压测、灾难恢复和 on-call runbook。
- 版本化 API/弃用策略、模板变更审计、灰度与回滚。

退出门禁：定义并达到可用性与延迟 SLO；安全评审和恢复演练通过；支持团队能从 request ID 定位问题；计费可对账且无已知重复收费路径。

### 阶段 4：视频与 coding 能力（分别立项）

目标：在独立威胁模型和资源模型下扩展新类别，而不是复用图片能力后直接宣称可用。

视频所需新增能力：长时任务、分片/转码、超大对象上传下载、预览、版权与内容审核、显著更严格的成本控制。

coding 所需新增能力：隔离沙箱、无默认网络、CPU/内存/时间/文件配额、依赖供应链策略、恶意输出检测和人工确认边界。

退出门禁：每个类别拥有自己的 RFC、威胁模型、成本模型、故障演练和验收清单；在此之前 UI 始终标记 coming soon。

## 4. 关键决策点

以下决策达到触发条件时再作，不提前引入复杂度：

1. **何时拆 worker**：阶段 1 需要独立扩缩容、部署隔离或 API 延迟受执行影响时。
2. **何时拆微服务**：只有不同团队需要独立发布、数据所有权清晰且模块化单体已成为明确瓶颈时；首版不拆。
3. **队列选型**：依据最大任务时长、延迟、重复投递、可见性超时、运维能力和云约束做 ADR，不由 SDK 偏好决定。
4. **供应商选择**：用质量、延迟、价格、幂等/查询/取消能力、数据政策和区域可用性做 PoC 评分。
5. **一致性**：run 数据库是状态真源；队列和回调只传递至少一次信号，不成为唯一事实来源。
6. **资产存储**：达到多实例或需保留/分享时迁移对象存储；URL 只是短期投影，asset ID 保持稳定。

## 5. 建议 ADR 队列

在相应阶段开始前，由协调者或对应 owner 建立并评审：

- ADR-001：首版模块化单体与 worker 分离触发条件。
- ADR-002：模板 revision、run snapshot 与兼容策略。
- ADR-003：生产数据库、队列和租约模型。
- ADR-004：对象存储、授权下载和资产保留。
- ADR-005：真实模型供应商评估与故障语义。
- ADR-006：租户模型、身份认证与授权边界。
- ADR-007：计费账本、成本归属与补偿。
- ADR-008：视频处理安全与媒体管线。
- ADR-009：coding 沙箱威胁模型。

## 6. 风险登记

| 风险 | 早期信号 | 缓解措施 | Owner 建议 |
| --- | --- | --- | --- |
| mock 被误认为真实生成 | 文案省略 mode；演示对外传播 | 三层 mock 标签、零成本、验收阻断项 | 产品/前端 |
| 重放导致重复收费 | 超时后自动重新 submit | attempt journal、external ID、unknown 状态 | 后端 |
| 模板变更破坏历史 retry | run 运行时读取最新版模板 | 不可变 revision + run snapshot | 后端/架构 |
| 取消被理解为撤销外部副作用 | UI 立即显示成功取消 | best-effort 语义、取消中可见、reconcile | 全栈 |
| 单机恢复被误称生产可靠 | 仅测优雅重启 | 强制终止、重复投递、队列/DB 故障演练 | 后端/SRE |
| 资产 URL 泄露或目录穿越 | URL 直接包含文件路径 | asset ID 查找、路径规范化、签名 URL | 后端/安全 |
| 多租户数据越权 | 查询只按 run ID | 每次读写带 tenant 作用域、授权测试 | 后端/安全 |
| coding 功能成为 RCE | 复用普通 worker 执行代码 | 独立沙箱项目、默认无网络、硬配额 | 安全/平台 |
| 视频成本失控 | 没有预算上限即开放 | 预估、配额、审批、强制 kill switch | 产品/平台 |

## 7. 最近下一步

阶段 0 期间按以下顺序收敛：

1. 以实施简报冻结当前 API，前后端只在协调者确认后改约定。
2. 后端先完成持久化状态机、幂等和确定性 mock adapter，再开放 UI 联调。
3. 前端围绕真实 API 状态实现轮询、错误、retry/cancel 和 mock 标签。
4. 集成后逐项执行 `docs/acceptance.md`，记录未通过项和限制。
5. 阶段 0 通过后再为阶段 1 写 ADR 与容量/威胁模型；不得提前把真实供应商接入标记为完成。
